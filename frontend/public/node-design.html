01 · The project in one minute

A database that can prove its answers.

Arkiv’s experimental node turns signed operations into durable, indexed state. A full node replays the work. A light node checks query proofs without keeping the entity database.

9009Rogue One test chain
3 rolesProducer · full · light
1 proposerPinned signing authority
This is a working prototype with real signatures, persistence and query proofs. It is not an Ethereum execution engine or a decentralized consensus network.

This presentation follows a transaction from the wallet to disk, then follows a query back to a verified answer. The final sections report the review findings and remaining limits.

02 · The moving parts

Each process has a different job.

Write

Wallet / SDK

Signs locally and sends a transaction.

→
Execute

Producer

Admits transactions, builds blocks, commits state and signs headers.

→
Replay

Full node

Re-executes blocks, compares commitments and serves proofs.

→
Verify

Light node

Retains authenticated headers and checks query witnesses.

The browser is a client

The light-node panel sends requests to the hosted Rust verifier. It checks response shape and bindings, then displays the result. It does not run the cryptographic verifier in JavaScript.

The explorer is a projection

A separate scanner and PostgreSQL service make chain activity easy to browse. That database is not the light node’s trust anchor and is not the authoritative node state.

04 · A write, step by step

One transaction has one atomic outcome.

Choose a stage to follow the work. This diagram explains the implementation; it does not submit a transaction.

Check the signed envelope

The producer checks canonical encoding, signer, chain identity, account nonce, limits and available funds. An invalid transaction is rejected before inclusion.

Failure is not always rejection

An included transaction whose operations fail rolls back its entity changes. It still consumes its transaction nonce and pays for charged work. A transaction rejected at admission is not an included failed transaction.

Expiry is part of execution

The block processes scheduled expirations before user transactions. Expired entities disappear from live rows and indexes together. Older snapshots retain their historical contents.

Each distinct typed value points to a posting set: all record IDs that carry that value.

A write maintains the row, key binding and affected postings in the same candidate state. This consistency is essential to completeness proofs.

u64(15) and dec(15) are different terms.

Branches share immutable structure with their parent snapshot. A checkpoint supports rollback; sealing and publication make a new state visible. A historical query selects the completed state of a particular block, not a moving “latest” view.

06 · What a state root means

A compact fingerprint of committed state.

Signed headerNames a block and its state root
State headerCommits catalog, host state, pricing and allocation metadata
Namespace catalogDescriptor + raw map + row map + key map + term index roots
Host mapAccounts, nonces and host-owned execution state
Term → complete posting set → row + key bindingThe links a query witness must establish

A Merkle Patricia trie combines ordered keys with hashes. A proof opens the needed paths and uses hashes for unrelated subtrees. Changing a committed value changes the reconstructed root.

A root binds data. A signature names the authority that accepted that root. Neither alone proves that the authority executed every rule correctly.

07 · Two different read paths

“The API returned it” is not “the proof verified”.

Read pathSupportsGuarantee
SDK / JSON-RPC queryBroader typed expressions, Boolean combinations, ranges, selection and paginationOrdinary read. A light node forwarding it does not add a proof.
Dedicated equality proofOne typed equality, paged rows at a fixed snapshotAuthenticates the posting set and exact requested page; continuation is verifier-controlled.
Dedicated numeric range proofOne indexed attribute; lower, upper or both bounds; inclusive or exclusiveComplete interval result or an error. No paging.
Account proofAccount state against an authenticated headerChecks committed account data; does not prove the entire execution history.

Choose a proof-capable endpoint explicitly. The availability of a broader SDK query does not imply that the same expression has a complete proof.

08 · Range completeness

Why can’t the server quietly omit price 15?

10 ≤ price < 20 over demo values 9, 10, 15, 20, 21 must return 10 and 15.

  1. Prove the entire typed interval

    Open every term-index branch that could intersect the bounds. An unexplained hash inside the requested interval cannot hide a matching term.

  2. Prove every ID under each value

    Reconstruct each matching term’s complete posting set. If three entities have price 15, supplying only one will not reproduce its commitment.

  3. Bind IDs to actual entities

    Authenticate rows and public key bindings, check the typed attribute, and check liveness at the selected block.

  4. Match the trusted snapshot

    The proof must bind the exact query, genesis, block height, block hash and state root accepted by the light node.

An empty result also needs a proof

10 < price < 15 proves an empty gap. An existing namespace with no matches is different from an unknown namespace or an unavailable block.

Bounded means explicit failure

The signed profile caps results at 64 rows and 64 matching terms, with additional proof-byte and work limits. Oversized queries fail; they do not quietly truncate.

09 · The trust boundary

What each “verified” statement establishes.

Full node: execution checked

Independently replays signed inputs and compares the resulting block commitments. This detects execution disagreement under the implemented rules.

Light node: answer checked

Authenticates headers under the pinned proposer and checks query witnesses against the accepted root. It does not replay all state transitions.

  • One authority. Rogue One has a single pinned proposer. There is no multi-party consensus or independent finality mechanism.
  • Correct indexes are assumed. A query proof cannot reveal a row that a malicious state producer never put into the committed index.
  • The browser trusts the hosted verifier. Independent verification requires your own verifier and trusted identity/proposer configuration.
  • Conflicts stop progress. Conflicting authenticated history must freeze following rather than silently switch roots.

10 · Durable publication

Do not acknowledge a head before its data is safe.

First

Build the exact candidate and its required objects.

→
Then

History

Durably acknowledge the signed body in history.redb.

→
Then

State

Atomically commit state, body reference, metadata, inclusions and head in node.redb.

→
Finally

Publish

Advance the visible head and remove included pool entries.

Storage outcomeSafe response
CommittedPublish the acknowledged candidate.
Not committedDo not advance. Retain the exact candidate and use explicit recovery/retry.
IndeterminateFence progress until recovery establishes the durable outcome; do not guess from an in-memory observation.

A crash between the two files can leave an unused history object. That is acceptable: the object is not inclusion. A committed state reference to missing or corrupt history is an error. Backups must preserve compatible state and history.

Light nodes retain certificates in headers.redb. Node state reopens without replaying every block, but the SDK’s derived transaction/hash lookup index still rebuilds from retained history.

11 · Wallet compatibility and GLM

Ethereum transaction encoding; native execution.

21,000Gas for a plain native transfer
1 gweiFixed gas price, fees burned
18Native GLM decimal places

Legacy EIP-155 and EIP-1559 signed transactions are accepted for the configured chain. SDK calls to the Arkiv system address decode into native entity operations. There is no general EVM, contract creation or arbitrary contract execution.

Fees and storage rent

The account profile debits real test GLM balances. Entity creation, growth and lifetime extension include deterministic occupancy charges. Gas estimation simulates disposable state and is not an affordability guarantee.

The faucet is finite

Its genesis allocation is 1 billion GLM. A 100-GLM drip plus a 0.000021-GLM transfer fee supports just under ten million drips. It is not an unlimited mint.

The 21,000-gas rule was activated with fresh chain 9009. Old chain data must retain its compatible executable; ordinary deployments must not recreate genesis.

12 · How it is operated

Keep identity, state and history together.

Public surfaces

  • Producer RPC: signed submissions and SDK reads.
  • Full panel: replay state and proof serving.
  • Light panel: verified equality and range examples.
  • Explorer: separately indexed activity.
  • Internal faucet: password-gated funding.

Operational facts

  • Genesis identity, run identity and signing authority must match.
  • The container stack separates producer, full and light processes.
  • Private keys and deployment credentials stay outside repositories.
  • Monitor follower lag, storage growth, proof-limit failures and fenced/conflicting health.
  • Query snapshots stay pinned even as the live head advances.
Read-only observation on 27 September 2026: full and light both reported “following” at block 32,092 with the same block hash and state root. This is a dated observation, not a continuous availability promise.

13 · Review results

Concrete findings, with evidence.

Fixed · medium severity · node

Remember signed headers even when the body is unavailable

Previously, the full follower remembered the sampled peer head but could forget an advertised intermediate header when its body fetch failed. A later conflicting signed header at that height could escape observation-based conflict detection.

The follower now durably records every authenticated advertised certificate before fetching bodies. A real-socket regression failed before the patch and now checks persistent conflict detection, an unchanged accepted head and no second body fetch.

Fix · Regression

Fixed · low severity · frontend

Reject malformed status before it reaches React

Status validation did not check the new proof-profile list or proposer display value. An object in either field could cause a rendering error. The client now rejects malformed data as a status error; regression cases cover both fields.

Fix · Regression

Fixed · low severity · validation

Compare the actual full/light chain identity

The deployment checker compared two missing nested identity objects, so its assertion passed without checking anything. It now requires and compares the top-level source, run, genesis, chain and authentication fields.

Corrected · documentation

Describe the implementation that exists today

Older architecture and proof documents still described durable nodes or range examples as future work. The signed-node overview also understated current Ethereum-envelope support. These statements were updated, and the RPC guide now explicitly says that “safe” / “finalized” are local-head aliases and “eth_syncing” is not a follower-progress signal.

No confirmed core proof-forgery or storage-atomicity defect was found in the reviewed paths. This is a scoped review result, not proof that no defects remain.

The storage reviewer also identified a serialized linear object-cache lookup. Its performance impact has not been measured; replacing it without evidence would add risk to the recovery gate.

14 · What is still open

The prototype’s boundaries are explicit.

BoundaryPractical implicationNext useful work
Single signing authorityNo public consensus, proposer rotation or multi-party finality.Specify the production trust and conflict-resolution model.
All history retainedBounded caches do not bound disk growth; restart lookup rebuilding grows with history.Define retention, proof-preserving pruning and snapshot bootstrap.
Limited complete proof profilesBroad SDK Boolean queries are unverified; large ranges fail instead of paging.Extend proof composition only with explicit completeness and work bounds.
RPC resource exposureJSON-RPC HTTP lacks the native REST concurrency gate; engine work can queue behind a mutex.Add measured admission/backpressure before exposing higher traffic.
Compatibility aliases“safe” and “finalized” mean local head; eth_syncing returns false.Use signed status for follower health; do not infer consensus finality.
Custom state commitmentsEthereum consensus clients cannot validate this chain as Ethereum.Keep compatibility claims scoped to tested application behavior.
Correct-execution assumptionA malicious proposer can commit an internally wrong index that a query proof cannot repair.Decide whether replay trust is sufficient or stronger execution guarantees are required.

These are design and production-readiness limits, not evidence that the implemented proof checks are fake. Keep the useful prototype small while making each additional guarantee explicit and testable.

  • Desktop/mobile presentation checks passed: all 15 sections, navigation, interactive stages, anchors and print/PDF.
