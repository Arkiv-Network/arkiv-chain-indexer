03 / IngestionOne block is the commit unit02:00–03:00

Bounded I/O. Atomic progress.

Walk blocks up to head − confirmationDepth. Resume from stored progress; retry a failed block until it succeeds.

  1. Fetch block + previous block. Full transactions feed inspection; the previous timestamp feeds block-time metrics.
  2. Fetch receipts with bounded workers. Default concurrency: 20. HTTP 429 retries happen per receipt with backoff + jitter.
  3. Compute and decode. bigint fee math; Arkiv metadata from the decoder. Optional balance reads use one RPC batch per block.
  4. Commit once. Only a successful database transaction advances the scanner checkpoint.
Single database transaction · schematic 
BEGIN
  UPSERT blocks
  REPLACE transactions + transaction_logs
  REPLACE transaction_operations
  REPLACE account_balances -- if enabled
  UPDATE transaction_records
  UPDATE scanner_state
  pg_notify(changed_entity_keys)
  pg_notify(stored_block)
COMMIT -- notifications become visible

Multi-row inserts reduce round trips. Logs and operations are chunked below PostgreSQL's bind-parameter limit.

Failure semanticsRPC, decoding, or database failure leaves the block pending. Decoder HTTP 400 means “not an Arkiv call”; other decoder failures trigger retry.

Source: scanner.ts · config.ts · storage.ts · arkivOperations.ts

Presenter · 1 min. Blocks advance sequentially within a scanner; receipts within a block use the current worker-pool implementation. AGENTS.md's sequential-receipt wording is older than this code. Five receipt attempts are allowed for rate limits before the whole-block retry takes over. Default confirmation depth is three. Balance snapshots are readings from the node, never sums of visible transfers. The transaction above is pseudocode, not executable SQL.

Presenter · 1 min. The LOWER expression is intentional: address queries are case-insensitive. Nonce is stored as text but sorted numerically through the expression index. 06 / Query costFetch wide rows only for the returned page05:00–06:00

Deep pages use a deferred join.

/transactions supports page numbers. Past page 1, the inner query walks keys; the outer join fetches the selected rows.

Simplified query · unfiltered, newest first 
SELECT t.*
FROM transactions t
JOIN (
  SELECT block_number, position
  FROM transactions
  ORDER BY block_number DESC, position DESC
  LIMIT $1 OFFSET $2
) k USING (block_number, position)
ORDER BY t.block_number DESC, t.position DESC;
  • Less heap work. A covered inner query can skip entries in the index; only page rows need full tuples.
  • Page 1 stays simple. No join overhead when there are no skipped rows.
  • Deterministic ordering. The primary key breaks ties; the outer ORDER BY is required.
  • Share the count. Pagination totals are cached by filter, independent of page, limit, or order.
Still O(offset)This reduces row-fetch cost; it does not remove the index walk. Autovacuum / visibility-map health and filter coverage determine the index-only benefit.

Source: storage.ts · queryTransactions · server.ts · transactionCountKey · valueCache.ts

Presenter · 1 min. The source records a roughly 6× improvement on a historical deep-page test; that is not a new benchmark or a universal guarantee. A cold exact COUNT(*) can still scan the full matching set. Concurrent identical count misses are coalesced. The row page and count are separate queries, not a shared database snapshot: ongoing ingestion can move offset pages. Blocks/ranges use block bounds; entity queries use a cursor instead.

Source: serve.ts · responseCache.ts · valueCache.ts · precomputedResponse.ts · serverConfig.ts

Presenter · 1 min. Notifications are delivered only after commit, and each serving process subscribes independently. This is bounded staleness, not strong read-after-write consistency: a request already waiting on an invalidated load can receive its result, but that result is not retained. LISTEN failure falls back to TTL. Precomputed sync refresh retains its previous value on computation failure; it is not a TTL-expiring cache. The 64 MiB limits budget cached bodies, not total process memory.
08 / Entity queriesProject state, then query typed values07:00–08:00

Temporal state with selective indexes.

The projector folds operations into entity versions. The query language compiles to parameterized SQL with attribute EXISTS predicates.

Read model
  • Version interval: [from_block, to_block). A live entity must also satisfy expires_at > query_block.
  • Head queries: partial indexes over to_block IS NULL AND NOT deleted; attribute equivalents use WHERE current.
  • Cursor order: (created_at, created_position, entity_key), all descending.
  • Bounded projection: key batches and a separate four-connection pool; late writes trigger refolding.
Actual secondary index shapes 
-- Address + liveness, head and history
(owner, expires_at)
(creator, expires_at)

-- Typed attribute equality / prefix
(name, type_id, value_text text_pattern_ops)

-- Exact numeric ranges
(name, type_id, value_num)

Pairing an address with expiry excludes expired candidates early. Typed attribute indexes avoid scanning arbitrary JSON for each predicate.

Coverage contractlatest means the projection head. Queries outside [floor, head] fail explicitly. Payload selection is refused; seeded chains need a genesis import.

Source: entityIndexStorage.ts · entityProjector.ts · entityQuerySql.ts · arkivJsonRpc.ts

Presenter · 1 min. A current version can still be expired: “current” means latest and undeleted, while expiry is evaluated for the requested block. Keeping expiry in the address index matters when an owner has a large history of expired entities. Historical indexes include every version. Numeric comparisons use exact NUMERIC, with decimals scaled to 18 places. The projector polls, detects late scans using scanned_at, and serializes fold writes with a PostgreSQL advisory lock.

Compress + validate

  • Prefer zstd level 1; fall back to gzip level 4.
  • Cached list variants derive from the same plain JSON.

03 / Batch and precompute

Remove repeated work

  • eth_getLogs resolves block hashes with one batched DB lookup.
  • Operation summaries load for the whole transaction page.
  • Guzzlers use minute buckets and Redis leaderboards refreshed by the scanner.
Bound responsesTransactions: ≤1,000 rows/page. Blocks / ranges / senders: ≤10,000 rows. Entity history: latest 100 operations by default, with truncation metadata.

Source: server.ts · frontend/api.ts · jsonRpc.ts · guzzlers.ts · guzzlerStore.ts

Presenter · 1 min. gzip matters because a CDN can request gzip from the origin even when browsers support other encodings. ETags reduce bytes; they do not necessarily eliminate query or serialization work on an uncached route. Guzzler buckets retain 24 hours of sender activity, and leaderboards refresh roughly once a minute. Core HTTP response caching is local to each backend; the Redis board is a separate precomputed read path.
10 / Operational limitsWhat to measure and where it can stall09:00–10:00

The bottlenecks are explicit.

Ingestion is constrained by upstream I/O; serving by cold query cost and database capacity. Caches and projections trade immediate freshness for less work.

Upstream & correctness

  • Receipt concurrency spends RPC rate budget; decoder outages block ingestion.
  • Confirmation depth adds lag. The scanner has no automatic reorg rollback.
  • Atomic checkpoints prevent partial-block progress; they do not prove chain finality.

Storage & freshness

  • Cold counts and deep offsets still scan. Index-only gains depend on vacuum.
  • Aggregates and entity projection have their own delay behind ingestion.
  • More API replicas mean more pools, caches, and cold misses against shared PostgreSQL.

Measure the path

  • Prometheus: HTTP latency / bytes, DB query latency / in-flight count, cache hit / miss / coalescing.
  • Route attribution through AsyncLocalStorage; bounded route / RPC-method labels.
  • Watch scanner and projection lag; inspect slow SQL plans before adding indexes.
RPC boundary/shadow-rpc/experimental serves indexed reads without passthrough. Protected /shadow-rpc can forward an allowlist to a rate-limited upstream; local responses expose missing stored fields as null.

Source: scanner.ts · serverMetrics.ts · db.ts · jsonRpcPassthrough.ts · docs/prometheus.md

Presenter · 1 min. The deck describes mechanisms in the checked-out source, not a new throughput benchmark. Use p95/p99 latency together with DB time, RPC errors, lag, and cache statistics to locate the limit. Session-based protected writes/RPC require the configured Origin and CSRF; temporary administrator tokens are also supported. Upstream configuration can override local methods through the allowlist. Raw /metrics exposure is controlled by deployment; /admin/metrics requires administrator access. Finish here and take questions.
